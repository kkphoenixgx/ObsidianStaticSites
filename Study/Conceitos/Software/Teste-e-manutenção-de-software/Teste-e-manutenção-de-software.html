Defeitos de software

  • Desenvolvimento de software é o processo de aquisição e detalhamento de informações

  • Erro = engano cometido por um humano, tornando um artefado incorreto.

  • Defeito = consequência do erro, bug. Causa uma não conformidade com as especificações. Esses defeitos podem estar também em requisitos, ma arquitetura, no projeto, na proposta ou nos próprios testes.

  • Falha = Execução inesperada.

  • Vulnerabilidade: Uma entrada ou condição peculiar que ocasiona um comportamento indesejado. Também são defeitos.

Não existe software perfeito e mesmo que seja, ainda podem existir falhas por vários motivos. Não tem como saber nem ter certeza disso.
Para saber se um módulo contém defeitos, existem os testes.

Toleramento de falhas. Caso aconteça, não é um software de qualidade:

  • fecha;
  • corrompe dados;
  • causa prejuízos;

Depuração

Busca por falhas. Identificar causa da falha, o defeito.

Depuração não é teste. Teste para ao achar.

Tecnicas de depuração

  • Força Bruta. 3 métodos de força bruta:
    • Análise e despejo de memória = Análise de valores de variáveis através de um arquivo que contém os valores das variáveis, o estado do sistema.
    • Uso de saída de dados = Famosos prints que modificam o código, que as vezes mascaram defeitos ou podem causar mais defeitos, embora seja muito bom.
    • Ferramentas de depuração = Marca os breakpoints e mostra os valores das variáveis.
  • Backtracking: Puramente analítica.
    • Analiza as chamadas das funções e vendo onde tá o defeito.
    • Eliminação de causa. Pensa nas causas que podem acontecer, testa a hipótese, se for corrige, se não pensa em outra hipotese. Que pode ser feita por dedução ou por indução.
  • Depuração por indução
    1. Coleta dados
    2. Estrutura os dados
    3. Identificação das relações
    4. Formular hipotese
    5. Prova da hipotese
    6. Correção do defeito

Testes e Depuração

De fato há uma relação simbiótica entre eles. De que adianta testar e não depurar?

Correções podem gerar defeitos: Eis as oerguntas de Van Vleck.

  1. O mesmo defeito acontece em outras partes do código?
  2. Quais novos defeitos podem ser gerados?
  3. O que deveria ter feito para evitar esse erro?
  1. Exercício: Força bruta, uso de saída de dados.
  2. Indução tem um passo a passo, uma análise deve ser feita para chegar uma hipotese, de fato debuggar, dedução é pensar na causa e testar a hipotese.
  3. Refazer o processo e tentar em outros lugares ou em um lugar mais específico até encontrar os defeitos.
  4. Formular uma nova hipotese e tentar prova-la novamente.
  5. Você injeta em um arquivo ou algo do tipo os valores das variáveis conforme o código roda e assim pode identificar onde está acontecendo a falha, em que momento do runtime e o que ocasionou aquela falha.

Princípios do teste de Software

Um bom teste se pauta em princípios fundamentais:

  1. Teste demonstra a presença de defeitos. Ele não afirma que não há defeitos, ele mostra que os defeitos existem quando encontrados
  2. Reduzem a probabilidade dos defeitos continuarem. Contudo, não afirma que o sistema está perfeito
  3. Teste exaustivo é impossível. Se cresce o programa, as vezes já adiciona infinitas entradas. Foco no maior risco e nas maiores possibilidades.
  4. Teste antecipado. Quanto mais rápido começa a testar, melhor.
  5. Os defeitos geralmente ficam em uma parte específicas do software
  6. Paradoxo do pesticida. O mesmo teste uma hora para de apontar novos defeitos. E para evitar isso, os testes devem ser atualizados.
  7. Teste depende do contexto.
  8. Ilusão da ausência de erros. Os testes não serão úteis se não atendem as espectativas do usuário.

Princípios complementares

  1. Testes devem ser planejados antes do início de sua execução.
  2. Um processo de teste deve incluir uma revisão detalhada dos resultados dos testes
  3. Os testes devem ser rastreáveis aos requisitos do usuário.
  4. Testes devem sempre abranjir o máximo mas partindo das partes mais importantes
  5. Testes devem ser feitos por uma equipe independente do programa.
  6. É desejável que a execução dos testes deva ser outros de quem planejou os testes.
  7. Recursos e cronogramas não devem ser definidos partindo que não terá erros.
  8. Metade do esforço é definir se o programa faz o que se espera. A outra metade é se ele faz o que não se espera.
  9. 80% das falhas estarão em 20% dos componentes do software. Princípio de Pareto.

Características de um bom teste

  • Deve conter alta probabilidade de revelar falhas.
  • Não cria testes redundantes.
  • Deve cobrir o mínimo de funcionalidades possível.
  • Deve ser o mais simples possível.

Mitos sobre testes

  • Dev e tester não são inimigos. O cliente falar é muito pior.
  • A equipe de test não é de devs menos qualificados.
  • Software pronto

Exercícos

  1. Quanto mais rápido começa a fazer os testes, mais rápido começa a encontrar bugs, menor o custo. Se os testes começam antes, dificílmente deixará de faze-los.
  2. Não. Se ele não consegue nem codificar, quem dirá identificar erros em softwares complexos e muito acima do nível do mesmo.
  3. Há de avaliar se o alvo da abranjência é idôneo para a definição se é ou não uma falha. Ademais, se pouco o cobre, pouco é capaz de não estar cobrindo o busílis.

Testes e qualidade

Papel dos testes na qualidade = Medir a qualidade. Os testes medem a confiança sobre o teste, aumenta a qualidade.

Um teste bem planejado, quando não encontra defeitos, reduz o nível do software e encontra defeitos.

A mera execução não agrega qualidade, só quando encontra as falhas, corrige os defeitos, somente aí agrega qualidade. Embora as correções agreguem o software, elas os degradam na medida que adicionam mais problemas.

Relação: Qualidade X Falhas = (Q = quadrante)

Q1 = Poucas falhas
Q2 = Muitas faljas
Q3 = Poucas falhas
Q4 = Poucas falhas

Se tem muitas falhas, se testes for bons, se a qualidade for ruim, encontrará muitas falhas e se for bom, encontrará poucas falhas.

Atividade

  1. Se você encontra falhas, sim, a qualidade do software será baixa.
  2. Ou que ele não contempla o que deve e, portanto, tem baixa qualidade no teste ou que o software de fato tem alta qualidade.
  3. Não, dependerá se erros são encontrados e se são corrigidos, somente a correção dos erros pode agregar qualidade ao software.

Bloco 1: Fundamentos, Qualidade e Psicologia

1. O Conceito e o Objetivo do Teste

  • Definição: O teste é o processo de execução de um programa com a intenção de encontrar erros.

  • O “Sucesso” do Teste (Pegadinha Clássica): * Um teste NÃO é bem-sucedido quando o sistema não apresenta falhas.

    • Um teste é BEM-SUCEDIDO quando ele encontra um erro ainda não descoberto.

  • Atividade Destrutiva: Psicologicamente, testar é tentar “quebrar” o software. É um erro pensar que testar serve para mostrar que o programa funciona.

2. Garantia (QA) vs. Controle (QC)

O professor costuma trocar as definições nestas duas. Guarde as palavras-chave:

  • QA (Garantia da Qualidade): Foco no PROCESSO. É preventiva. Serve para melhorar a forma como o software é feito para que erros não sejam criados. (Ex: Auditorias, padrões de código).
  • QC (Controle da Qualidade): Foco no PRODUTO. É reativa/detetiva. São as atividades técnicas (como o teste em si) para encontrar defeitos no que já foi produzido.

3. Verificação vs. Validação (V&V)

Outro ponto de obsessão nas provas:

  • Verificação: “Estamos construindo o produto corretamente?“. Avalia se o software segue as especificações, requisitos técnicos e normas. (Foco no papel/especificação).
  • Validação: “Estamos construindo o produto correto?“. Avalia se o software atende às necessidades reais do usuário final. (Foco no uso/cliente).

4. Psicologia dos Testes (Ficheiro 15)

  • Independência: O desenvolvedor tem um “viés construtivo” e pontos cegos sobre a própria obra. O teste deve ser feito por alguém independente para garantir objetividade.
  • Níveis de Independência: O material cita que a eficácia aumenta conforme a independência cresce (do próprio autor → outro colega → equipe interna de QA → consultoria externa).
  • Comunicação: O testador deve ser neutro e focar no sistema, nunca criticar a pessoa do desenvolvedor, para evitar conflitos de ego.

5. Os 7 Princípios Gerais (Ficheiro 6)

Estes aqui você deve saber de cor para as questões de V/F:

  1. Teste demonstra a presença de defeitos: Testar prova que há bugs, mas não prova que o sistema é perfeito (ausência de defeitos é impossível de provar).
  2. Teste exaustivo é impossível: Exceto para casos triviais, não dá para testar todas as combinações. Usamos análise de risco para priorizar.
  3. Teste Antecipado (Early Testing): O teste deve começar assim que houver requisitos.
    • Curva de Custo de Boehm: Corrigir um erro nos requisitos custa 1x. Corrigir o mesmo erro em produção custa 100x.
  4. Agrupamento de Defeitos (Pareto): 80% dos erros estão em 20% dos módulos. Se achar muitos bugs num lugar, continue cavando ali.
  5. Paradoxo do Pesticida: Se você repetir os mesmos testes sempre, o sistema fica “imune” e você não acha bugs novos. É preciso revisar e atualizar os casos de teste.
  6. Teste depende do contexto: Um software de avião é testado diferente de um site de notícias.
  7. Falácia da ausência de erros: De nada serve um software sem bugs se ele for inútil ou não atender ao cliente.

6. Princípios Adicionais de Myers

O teu material traz extras do Myers que também caem:

  • Rastreabilidade: Cada teste deve estar ligado a um requisito de usuário.
  • O Lado do “Não”: Testar se o programa faz o que deve é só 50% do trabalho. A outra metade é testar se ele não faz o que não deve fazer.
  • Planejamento: Testes devem ser planejados muito antes da execução (conforme o Modelo V).
  • Independência de Execução: Idealmente, quem executa o teste não deve ser quem o planejou, para evitar o olhar viciado.

Bloco 2 (Erro, Defeito, Falha e Taxonomia de Shull)

Este bloco é o preferido do professor Octávio para questões de “relacione as colunas” ou cenários onde tu precisas de identificar o momento exato em que a “merda” aconteceu.

1. A Cadeia de Causalidade (A Linha do Tempo)

Não podes confundir estes três termos. Existe uma ordem lógica e temporal:

  1. ERRO (Engano): É uma ação humana (mental ou física). Ocorre na cabeça do desenvolvedor ou analista.
    • Exemplo: O programador entende que o desconto é de 10%, mas o requisito dizia 15%.
  2. DEFEITO (Bug/Falta): É a manifestação física do erro num artefato (documento de requisito, diagrama ou código). O defeito fica “adormecido” lá.
    • Exemplo: A linha de código escrita como valor * 0.10 em vez de valor * 0.15.
  3. FALHA: É o desvio visível do comportamento esperado durante a execução. É quando o utilizador (ou o testador) percebe que algo deu errado.
    • Exemplo: O cliente final vê que o total da compra está mais caro do que deveria.

A Pergunta “Filha da Puta”: * Pergunta: “Todo defeito gera uma falha?”

  • Resposta: NÃO. Um defeito pode estar num trecho de código que nunca é executado (código morto) ou sob condições que nunca ocorrem. Para haver falha, o código defeituoso precisa de ser executado.

2. Vulnerabilidade

O teu material introduz este conceito aqui:

  • Vulnerabilidade é um defeito que pode ser explorado por uma ameaça externa para comprometer a segurança (confidencialidade, integridade ou disponibilidade).
  • Resumo: Todo defeito de segurança é uma vulnerabilidade, mas nem todo defeito (ex: cor errada de um botão) é uma vulnerabilidade.

3. Propagação de Defeitos

O material enfatiza que o software é construído em camadas.

  • Se o Erro acontece no Requisito → gera um Defeito no documento de Análise → que gera um Defeito no Design → que gera um Defeito no Código → que explode numa Falha em produção.
  • Conclusão: Quanto mais cedo o erro ocorre, mais “filhos” (defeitos derivados) ele deixa pelo caminho.

4. Taxonomia de Shull (O Coração do Bloco 2)

Esta é a parte que os alunos costumam negligenciar e onde o professor Octávio cobra os detalhes. Shull classifica os defeitos encontrados em artefatos de software (especialmente em inspeções de documentos). São 7 categorias:

  • Omissão: Quando uma informação necessária para o desenvolvimento do software não foi incluída no artefato (ex: esquecer de especificar o que acontece quando o estoque chega a zero).
  • Ambiguidade: Quando a informação presente permite duas ou mais interpretações distintas, gerando dúvida no desenvolvedor (ex: “o sistema deve ser rápido” — rápido quanto?).
  • Inconsistência: Quando duas ou mais partes de um documento (ou documentos diferentes) fornecem informações que se contradizem (ex: a página 5 diz que o botão é azul e a página 20 diz que é verde).
  • Fato Incorreto: Quando a informação está presente e é clara, mas está errada em relação ao domínio do problema ou à realidade externa (ex: dizer que um CPF tem 12 dígitos).
  • Informação Estranha: Quando se inclui informação que não pertence ao domínio do problema ou que é totalmente desnecessária para o software (o famoso “encher linguiça”).
  • Redundância: Ocorre quando a mesma informação é repetida desnecessariamente em diferentes partes do artefato, o que pode dificultar a manutenção futura (se mudar num lado, tem de mudar em todos).
  • Não conformidade com padrões: Quando o documento viola os padrões de qualidade, modelos (templates) ou normas estabelecidas pela organização ou pelo projeto.

5. Teste vs. Depuração (Debugging)

Cuidado para não achar que são a mesma coisa! O arquivo 3 - Depuração.pdf é curto mas perigoso:

  • Teste: Atividade de encontrar a falha (viés destrutivo).
  • Depuração (Debugging): Atividade de localizar a causa do defeito e corrigi-lo (viés construtivo, feita pelo desenvolvedor).

Técnicas de Depuração citadas no material:

  1. Força Bruta: Encher o código de “prints” ou carregar despejos de memória (dump) para ver onde ele morre. É a mais comum, mas a menos eficiente.
  2. Backtracking: Começa onde a falha ocorreu e vai voltando no código manualmente para ver onde a lógica se perdeu.
  3. Eliminação de Causa: Lista todas as causas possíveis e vai testando uma a uma até sobrar a real.

Metodologias de Depuração:

  • Indução: Partes dos dados particulares (os sintomas) para criar uma hipótese geral.
  • Dedução: Partes de causas gerais possíveis e vai eliminando até chegar ao caso específico.

6. Considerações Finais do Material

  • Não existe software perfeito: O processo de desenvolvimento é humano, logo, o erro é intrínseco.
  • O custo da correção: Reafirma que corrigir em produção é até 100x mais caro.

Bloco 3 (IEEE 829, Modelo V e o Modelo Tridimensional da Estratégia)

O Modelo Tridimensional da Estratégia (O Cubo)

Imagine um cubo. Para definir “como vamos testar”, você precisa tomar decisões em três eixos independentes. O erro comum (a rasteira) é achar que uma decisão trava a outra.

  • Eixo 1: Nível de Teste (QUANDO): É a fase do desenvolvimento. (Unidade, Integração, Sistema, Aceite).
  • Eixo 2: Tipo de Teste (O QUÊ): É o atributo de qualidade.
    • Funcional: O sistema faz o que deve? (Regras de negócio).
    • Não-Funcional: O sistema é rápido? Seguro? Fácil de usar? (Performance, Segurança, Usabilidade).
  • Eixo 3: Técnica de Teste (COMO): É a metodologia.
    • Caixa Branca: Vejo o código.
    • Caixa Preta: Não vejo o código, foco nos requisitos.
    • Caixa Cinza: Vejo a arquitetura/banco de dados, mas testo as funções.

A Maldade do Professor: Ele vai te perguntar se “Teste de Unidade é sempre Caixa Branca”. Resposta: FALSO. Você pode fazer um teste de unidade (Nível) funcional (Tipo) usando Caixa Preta (Técnica), apenas injetando entradas no método e vendo a saída. As dimensões são ortogonais (independentes).

IEEE 829 - O Processo de Teste

Primeiro entende as fases e depois os artefatos com as fases. O nome das frases tem que estar bem claro na sua cabeça, tem que ser um mantra.

O material define que um processo estruturado não serve apenas para “organizar”, mas para garantir repetibilidade e objetividade. Aqui está o que tu precisas de saber sobre cada fase e exatamente o que tem dentro de cada documento:

A. Planeamento (Fase 1)
  • Objetivo: Definir a “lei” do teste para aquele projeto.
  • O Artefato: Plano de Teste. (Cuidado: É um documento de gestão!).
  • O que tem dentro (O Octávio adora cobrar isto):
    1. Escopo: O que será testado e, muito importante, o que NÃO será testado.
    2. Critérios de Passagem/Falha: O que define se o sistema passou no teste global.
    3. Critérios de Entrada: Condições mínimas para começar (ex: código compilado).
    4. Critérios de Saída: Quando paramos (ex: 100% de cobertura, zero bugs críticos).
    5. Critérios de Suspensão e Retomada: Se o sistema estiver tão podre que não dá para testar, paramos tudo. O que nos faz voltar?
    6. Recursos e Cronograma: Quem faz o quê e quando.
    7. Riscos: Riscos de software e riscos do próprio processo de teste.
B. Preparação / Projeto (Fase 2)
  • Objetivo: Analisar os requisitos para saber onde o teste deve atacar.
  • O Artefato: Especificação do Projeto de Teste (Test Design Spec).
  • O que se faz aqui: Identificam-se as Condições de Teste. É o momento de “modelar” o teste, antes de escrever o passo-a-passo.
C. Especificação (Fase 3) → A Batalha dos Artefatos

É aqui que a maioria dos alunos erra. Tu tens de saber a diferença exata entre estes dois:

  1. Caso de Teste (O QUÊ):

    • Conteúdo: Identificador, item de teste (funcionalidade), entradas (valores exatos), pré-condições e o resultado esperado.
    • Dica de Ouro: Falou em “valor de entrada” ou “comportamento esperado”, é Caso de Teste.

  2. Procedimento de Teste / Roteiro (COMO):

    • Conteúdo: A sequência de ações. Passo 1: Abra o browser. Passo 2: Digite a senha. Passo 3: Clique em enviar.
    • Dica de Ouro: É o manual que permite que qualquer pessoa execute o teste sem ter desenvolvido o sistema.
D. Execução (Fase 4)
  • O Artefato: Log de Teste.
  • O que é: O registro cronológico da execução. Diz quem testou, quando testou, qual caso foi usado e se o resultado foi Pass ou Fail.
E. Avaliação (Fase 5)
  • O Artefato: Relatório Sumário de Teste.
  • O que é: O resumo para os chefes. Contém métricas (quantos bugs achamos, quantos faltam corrigir) e a conclusão: “O software está apto para ir para produção?“.
1. A Vinculação Documental (Hierarquia IEEE 829)

Imagina isto como uma pirâmide. O que é decidido no topo (Plano) tem de chegar à base (Log) através de documentos intermediários.

Fase do ProcessoDocumento Gerado (Artefacto)Vinculação / O que “herda” do anterior
1. PlaneamentoPlano de Teste (Test Plan)Herda os Requisitos de Utilizador e define o Escopo (o que testar e o que não testar).
2. Preparação / ProjetoEspecificação de Projeto de Teste (Test Design Spec)Lê o Plano e identifica as Condições de Teste (ex: “Testar login com campos vazios”).
3. EspecificaçãoEspecificação de Caso de Teste (Test Case Spec)Pega na “Condição” e define as Entradas Reais e o Resultado Esperado.
3. Especificação (cont.)Especificação de Procedimento de Teste (Test Procedure Spec)Pega no Caso de Teste e cria o Passo-a-Passo (Roteiro) para o executor.
4. ExecuçãoLog de Teste (Test Log)Regista a execução cronológica do Procedimento.
4. Execução (Erro detetado)Relatório de Incidente (Incident Report)Vincula a Falha encontrada ao Caso de Teste que falhou.
5. AvaliaçãoRelatório Sumário de Teste (Test Summary Report)Consolida todos os Logs e Incidentes para dar o veredito final.

A Regra de Ouro da Vinculação:

  • Caso de Teste → Foca no DADO (Entrada/Saída).
  • Procedimento de Teste → Foca na AÇÃO (Passos/Cliques).
  • Rastreabilidade: É a capacidade de olhar para um Log e saber qual Requisito ele está a validar.
2. As Três Dimensões da Estratégia (O Modelo 3D)

Para não te confundir: a Estratégia não é um documento isolado, ela é o “como” que preenche o Plano de Teste. Ela divide-se em 3 eixos independentes (Ortogonais).

Eixo A: Níveis de Teste (O “QUANDO”)

Define a maturidade do código.

  1. Unidade: O mais pequeno (método/classe).
  2. Integração: A interface entre dois módulos.
  3. Sistema: O software completo (fim-a-fim).
  4. Aceite: Validação final pelo cliente.
Eixo B: Tipos de Teste (O “O QUÊ”)

Define o objetivo da avaliação.

  • Funcionais: Regras de negócio (o que o sistema faz).
  • Não-Funcionais: Atributos de qualidade (Performance, Segurança, Usabilidade, Resiliência, Carga, Estresse).
    • Dica: O Ficheiro 12 detalha estes tipos, mas eles “moram” aqui nesta dimensão da estratégia.
Eixo C: Técnicas de Teste (O “COMO”)

Define a metodologia de criação dos testes.

  • Caixa Branca (Estrutural): Conheço o código. Testo caminhos lógicos, ciclos e condições.
  • Caixa Preta (Funcional): Não vejo o código. Só me importo com Entradas e Saídas baseadas nos requisitos.
  • Caixa Cinza: Conheço um pouco da estrutura (ex: base de dados), mas testo as funcionalidades.
3. Detalhes Cruciais de Processo (Onde o Octávio te apanha)

Existem três estados especiais no processo estruturado que tens de saber:

  1. Critérios de Suspensão: Não é um erro qualquer. É quando algo bloqueia a continuidade. Se o servidor de teste cai, eu suspendo o processo.
  2. Critérios de Retomada: O que tem de acontecer para eu voltar a testar? (ex: “Servidor online e base de dados restaurada”).
  3. Critérios de Saída: Nunca é “quando eu achar que está bom”. Tem de ser métrico (ex: “95% dos casos passados e 0 bugs críticos”).
4. Resumo da “Lógica de Vinculação” para a Prova:

Se o professor te der um componente de um documento e perguntar a qual ele pertence:

  • “Conjunto de passos ordenados” → Procedimento/Roteiro.
  • “Lista de riscos e recursos financeiros” → Plano.
  • “Valor de entrada X e Resultado esperado Y” → Caso de Teste.
  • “Identificação das características a serem testadas” → Projeto/Design.
  • “Passo-a-passo para o desenvolvedor ver o erro” → Incidente.

Modelo V

1. O Conceito do Modelo V

O Modelo V não é apenas um desenho bonito; ele é uma representação do ciclo de vida que resolve o problema do “teste apenas no fim”.

  • Lado Esquerdo (Descida): Fases de Desenvolvimento (Decomposição e Definição).
  • Lado Direito (Subida): Fases de Teste (Integração e Validação).
  • O “Veredito”: Para cada fase de desenvolvimento no lado esquerdo, existe um nível de teste correspondente no lado direito.
2. As Correspondências Obrigatórias (Decore isto!)

O Octávio adora colocar uma fase da esquerda e perguntar qual o teste da direita que a valida. A regra é a simetria:

  1. Requisitos de Utilizador / Negócio ↔ Teste de Aceitação
    • Lógica: O cliente disse o que queria no início; no final, ele testa se recebeu o que pediu.
  2. Requisitos do Sistema / Análise ↔ Teste de Sistema
    • Lógica: Analisámos como o sistema deveria ser; agora testamos o software completo (fim-a-fim).
  3. Projeto de Arquitetura (Design de Alto Nível) ↔ Teste de Integração
    • Lógica: Definimos como os módulos conversam entre si; agora testamos se essa conversa (interfaces) funciona.
  4. Projeto Detalhado / Codificação ↔ Teste de Unidade
    • Lógica: Escrevemos o código do método/classe; agora testamos se aquele pedacinho funciona isolado.

Req. Cliente → Req. Sistêmico → Projeto arquitetura → Código

Tsste aceite ← Teste sistema ← Teste integração ← Teste unidade

3. A Regra de Ouro: Testagem Simultânea

Esta é a maior “pegadinha” de V/F: “No Modelo V, o teste só começa quando a codificação termina.” → FALSO!

  • O Planeamento e a Modelação de cada nível de teste começam durante a fase de desenvolvimento correspondente.

  • Exemplo: Enquanto os analistas estão a escrever os Requisitos de Sistema, os testadores já estão a escrever o Plano de Teste de Sistema.

  • Objetivo: Detetar erros nos documentos antes mesmo do código existir (Verificação).

4. Características de um Bom Ciclo de Testes (Segundo o Modelo V)

O material destaca quatro pontos que costumam cair como questões de múltipla escolha:

  1. Para cada atividade de desenvolvimento, há uma atividade de teste correspondente.
  2. Cada nível de teste tem objetivos específicos para aquele nível.
  3. A análise e modelagem de testes começam durante a atividade de desenvolvimento.
  4. Testadores participam na revisão dos documentos assim que as primeiras versões estão disponíveis.
5. Verificação vs. Validação no Modelo V
  • Verificação (Lado Esquerdo): Ocorre enquanto descemos. Avaliamos se os documentos e o código estão a ser feitos conforme as normas. “Estamos a construir o produto corretamente?“.
  • Validação (Lado Direito): Ocorre enquanto subimos. Executamos o software para ver se ele faz o que o utilizador quer. “Estamos a construir o produto correto?“.

Bloco 4: Teste de Integração (O “Encaixe”)

O objetivo aqui não é saber se um módulo funciona sozinho (isso é Unidade), mas sim se a conversa entre dois ou mais módulos funciona corretamente.

1. Dois Subníveis de Integração (Cuidado!)

O material (Ficheiro 11) faz uma distinção que cai muito em questões de “V/F”:

  • Integração de Componentes: Foca na interação entre módulos/classes dentro do mesmo sistema.

  • Integração de Sistemas: Foca na interação entre sistemas diferentes ou entre o sistema e a infraestrutura (ex: o teu software a falar com a API do Banco ou com o Sistema Operativo).

2. A Abordagem “Big Bang”

  • O que é: Desenvolvem-se todos os módulos e tenta-se integrar tudo de uma vez no final.

  • Vantagem: Parece mais rápido… no papel.

  • Desvantagem (A Rasteira): É um caos. Quando algo falha, é quase impossível isolar em qual interface está o erro. O material diz que esta abordagem deve ser evitada em sistemas complexos.

3. Integração Incremental: Top-Down vs. Bottom-Up

Aqui é onde o Octávio mais “brinca” com diagramas. Para saberes o que usar, olha para onde a seta aponta.

A. Top-Down (De Cima para Baixo)

Começamos pelo módulo principal (o “Cérebro”) e vamos descendo para os módulos de suporte.

  • O Problema: Quando testamos o topo, os módulos de baixo (os “filhos”) ainda não estão prontos.

  • A Solução (STUBS): Usamos Simuladores (Stubs). Um Stub é um “pedaço de código burro” que apenas recebe a chamada do pai e devolve um valor fixo para o teste não travar.

  • Ponto Chave: Testa as funções de controlo e o fluxo principal cedo.

B. Bottom-Up (De Baixo para Cima)

Começamos pelos módulos da base (os que não dependem de ninguém, ex: funções de BD) e vamos subindo.

  • O Problema: Quando testamos a base, o módulo que deveria chamá-la (o “pai”) ainda não existe.

  • A Solução (DRIVERS): Usamos Controladores (Drivers). Um Driver é um programa de teste que “finge” ser o pai para disparar os dados para o módulo inferior.

  • Ponto Chave: Bom para sistemas onde a base técnica é o mais crítico.

4. A Tabela da Salvação (Memoriza isto!)

EstratégiaComeça por…Se faltar o outro lado, usa…Foco Principal
Top-DownMódulo de Elite (Topo)STUBS (Simuladores)Lógica de negócio e fluxo.
Bottom-UpMódulos Atómicos (Base)DRIVERS (Controladores)Desempenho e entrada de dados.

5. Integração Ad-Hoc ou “Sanduíche”

O material também menciona a abordagem mista, onde se usa Top-Down para as camadas superiores e Bottom-Up para as inferiores, encontrando-se no meio. É complexa de gerir, mas aproveita o melhor dos dois mundos.

A “Maldade Final” de Integração:

O professor pode dar-te um desenho com módulos A, B e C, onde A chama B e B chama C. Se ele perguntar: “Para testar o módulo B de forma isolada na abordagem Bottom-Up, o que é necessário?”

  • Raciocínio: Bottom-Up sobe. Se estou em B, o de baixo (C) já existe, mas o de cima (A) não.
  • Resposta: Um Driver para substituir o A.

Bloco 5: P2 - JUnit 5 (Ciclo de Vida e Asserções)

Este bloco define o comportamento básico do teste no código, focado na técnica de Caixa Branca (Testes de Unidade/Integração).

Anotações de Ciclo de Vida (Setup & Teardown):

  • @Test: Define que o método é um teste padrão.
  • @BeforeEach: Roda antes de cada método de teste.
  • @AfterEach: Roda depois de cada método de teste.
  • @BeforeAll: Roda uma única vez antes de todos os testes da classe. CUIDADO (Lição de Prova): No JUnit 5, métodos com @BeforeAll (e @AfterAll) obrigatoriamente precisam ter a assinatura static.
  • @AfterAll: Roda uma única vez após todos os testes.
  • @Disabled: Pula (desabilita) o teste.

Asserções (A Verificação do Resultado):

  • fail("mensagem"): Força a falha do teste imediatamente.
  • assertEquals(esperado, obtido): Verifica se os valores são iguais.
  • assertNotEquals(esperado, obtido): Verifica se são diferentes.
  • assertTrue(condicao) / assertFalse(condicao): Verifica lógicas booleanas.
  • assertNull(objeto) / assertNotNull(objeto): Verifica a existência (ou não) de instâncias em memória.
  • assertSame(esp, obt) / assertNotSame(esp, obt): Verifica se apontam para o mesmo endereço de memória (não apenas se os valores são iguais).

Asserções de Exceções (Pegadinha Clássica de Prova):

  • assertThrows(Exception.class, () -> { metodo(); }): Verifica se o método lança a exceção esperada.
  • assertDoesNotThrow(() -> { metodo(); }): Verifica se o método NÃO lança exceção. (Atenção: Na prova antiga (PF) houve a tentativa de escrever assertNotThrown, mas a sintaxe correta e exigida é assertDoesNotThrow).

Bloco 6: P2 - JUnit 5 (Testes Parametrizados e DDT)

Testes parametrizados (Data-Driven Testing - DDT) rodam o mesmo teste várias vezes com dados diferentes. Usa-se @ParameterizedTest no lugar de @Test. A prova P2 cobrou pesado a transição de sintaxe e as restrições de cada anotação.

Fontes de Dados (Sources):

  • @ValueSource(ints = {1, 2, 3}): Passa valores estáticos simples. Lição de Prova (P2): Limitado a um único argumento unidimensional por vez (ex: apenas uma String por vez). Não serve se a prova pedir para passar um “par” de valores simultaneamente (como um input e um output esperado).
  • @CsvSource({"21, 100", "42, 200"}): Passa pares/conjuntos de valores diretamente no código, separados por vírgula.
  • @CsvFileSource(files = "caminho/arquivo.csv", numLinesToSkip = 1, delimiter = ';'): Lê dados de um arquivo externo.
    • Lição de Prova (P2): Se o arquivo tem cabeçalho ou dados inúteis nas primeiras linhas, use numLinesToSkip. Ex: Para começar a ler a partir da 5ª linha, o parâmetro exato é pular as 4 primeiras usando numLinesToSkip = 4.
  • @MethodSource("nomeDoMetodo"): Busca os dados em um método Java.
    • Lição de Prova (P2 e PF): Se o enunciado disser “fornecidos por meio de um método de provimento de argumentos intitulado testJSONParaCoordenadaData”, você tem que usar @MethodSource("testJSONParaCoordenadaData"). Esse método deve retornar uma Stream<Arguments>. Tentar usar um CSV ou arquivo externo quando o enunciado exige método resultará em perda grave de pontos na avaliação do código, pois quebra a arquitetura pedida.

Bloco 7: P2 - Katalon Studio (Automação Web)

Aqui o teste simula um usuário real interagindo com a interface gráfica. É o topo do Modelo V (Testes de Sistema / E2E - Técnica de Caixa Preta).

Interação com o DOM (API WebUI):

  • WebUI.openBrowser("url"): Abre o navegador no site.
  • WebUI.closeBrowser(): Fecha o navegador.
  • WebUI.selectOptionByValue(testObject, <value>): Seta o valor de um
  • findTextObject('<path/id>') = Pega determinado objeto de teste, um TestObject
  • WebUI.click(findTestObject("botao")): Clica em um elemento.
  • `WebUI.setText(findTestObject(“input”), “valor”): Seta o texto de uma tag HTML.
  • WebUI.verifyElementText(...): Valida se o texto dentro do elemento bate com o esperado.
  • WebUI.verifyElementAttributeValue(...): Verifica propriedades específicas.

Ciclo de Vida Condicional (Hooks de Finalização): O Katalon permite fechar ou limpar o ambiente dependendo do resultado do teste. Esta é a maior pegadinha da P2 e PF:

  • @SetUp: Roda antes de tudo (bom para openBrowser).
  • @TearDown: Roda no final, não importa o que aconteça.
  • @TearDownIfPassed: Roda APENAS se o teste foi um sucesso. (Lição de Prova: “o navegador deve ser fechado apenas se este tiver sido bem-sucedido” = usar esta anotação englobando o closeBrowser).

A diferença crucial (Sempre cobrado):

  • @TearDownIfFailed: Roda se a asserção falhou (Ex: você esperava que o resultado fosse 10, mas o site mostrou 5. O teste rodou perfeitamente, mas a regra de negócio/matemática falhou).
  • @TearDownIfError: Roda se o script quebrou (Ex: o site caiu, a internet desconectou, ou o Katalon não achou o elemento HTML para clicar. É um erro de infraestrutura/código, e não uma falha de regra de negócio).

Não tá tudo na matéria mas é muito importante

  • Complexidade Ciclomática (CCN): Mensuração da quantidade de caminhos lógicos independentes em uma função para evitar códigos excessivamente densos e de difícil manutenção.
  • Cobertura de Teste (Test Coverage): Métrica que indica a porcentagem do código-fonte que é efetivamente executada pela suíte de testes.
  • Testes de Mutação (Mutation Testing): Técnica de modificar deliberadamente a lógica do código (ex: trocar operadores) para verificar se os testes existentes são capazes de detectar a falha.
  • Tamanho de Módulos: Definição de limites de linhas de código por arquivo para prevenir a existência de “God Files”.
  • Estrutura de Dependências: Análise do acoplamento entre os componentes do sistema para garantir integridade arquitetural.
  • Injeção Circular: Identificação de dependências recíprocas entre módulos que impedem o desacoplamento.
  • Arquitetura de Camadas: Verificação de fluxos de chamada proibidos (ex: Controller chamando Model diretamente) e uso de módulos de API para isolar implementações.
  • Análise Estática: Auditoria automatizada do código-fonte realizada no pipeline de CI para garantir padrões de qualidade antes do merge.
  • Análise de Vulnerabilidade: Checagem de falhas de segurança conhecidas em bibliotecas e pacotes de terceiros.
  • Teste Unitário: Validação isolada da menor unidade lógica funcional.
  • Instrumentation Test: Testes que dependem da interação com o ambiente de execução.
  • Pen Test (Teste de Intrusão): Avaliação ativa da segurança do sistema através de simulações de ataques.
