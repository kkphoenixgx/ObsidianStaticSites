A anotação @ValueSource suporta apenas um único argumento unidimensional por execução (ex: uma String, um Int). Para injetar um "par" de valores simultaneamente (como um input e um output esperado), você seria obrigado a usar @CsvSource ou @MethodSource.

Gestão de Estado no Katalon (Questão 5): Na P2, houve confusão entre falha de asserção e erro de execução. Nos rascunhos da PF, você anotou corretamente a divisão entre Failed e Error para a regra de fechamento do navegador em caso de teste malsucedido (@TearDownIfFailed e @TearDownIfError).

Embora a nota final da codificação não esteja detalhada linha a linha, seus rascunhos na Questão 4 indicam alguns riscos sintáticos na implementação do JUnit 5:

Modelo V: Exige simetria rigorosa.

Taxonomia de Shull: Aplica-se exclusivamente à inspeção estática de documentos (Omissão, Ambiguidade, Inconsistência, Redundância). Não possui relação com métricas dinâmicas como impacto ou probabilidade.

Gestão de Anomalias:

    A taxonomia exata dita a cadeia: Erro (humano) gera Defeito (estático) que resulta em Falha (dinâmico).

    O ciclo de depuração não é terminal. Se um defeito é corrigido, a próxima etapa obrigatória é a execução de Testes de Regressão para garantir a estabilidade do artefato.

Normatização ISO/IEC 25010 e IEEE 829:

    ISO 25010: Fixação de atributos primários e secundários (ex: Coexistência, Eficiência de Desempenho).

    IEEE 829: Separação de responsabilidades documentais. Caso de Teste foca em entradas e saídas esperadas; Procedimento de Teste foca no roteiro de cliques e ações.

Eixo 2: Automação Orientada a Dados (Carga da P2)

JUnit 5 (Domínio Funcional/Unidade):

    Ciclo de Vida: Anotações globais como @BeforeAll e @AfterAll exigem que a assinatura do método seja obrigatoriamente static.

    Parametrização (DDT):

        @ValueSource: Limitado a arrays unidimensionais simples (ex: apenas uma String por vez).

        @CsvFileSource: Domínio dos parâmetros de formatação (delimiter, numLinesToSkip) para contornar cabeçalhos de arquivos físicos.

        @MethodSource: Obrigatório quando o provedor de dados precisa instanciar e injetar objetos complexos no teste.

    Asserções de Exceção: A validação de que uma exceção não ocorreu utiliza assertDoesNotThrow(). A validação de que ocorreu utiliza assertThrows(ClasseDaExcecao.class, () -> { ... }).

Katalon Studio (Domínio E2E/Interface):

    Gestão de Estado Condicional: Distinção absoluta entre anomalias.

        @TearDownIfFailed: Executado quando a asserção da regra de negócio não confere (o teste rodou, mas o resultado matemático está errado).

        @TearDownIfError: Executado quando o script quebra (o elemento HTML não foi encontrado na tela).

A P2 é puramente operacional. Aqui você não foca no “por que” testar, mas no “como” testar e automatizar, usando as ferramentas certas para cada nível. Bloco 1: JUnit 5 - Ciclo de Vida e Asserções (Caixa Branca / Unidade)

Este bloco define o comportamento básico do teste no código.

Anotações de Ciclo de Vida (Setup & Teardown):

    @Test: Define que o método é um teste padrão.

    @BeforeEach: Roda antes de cada método de teste.

    @AfterEach: Roda depois de cada método de teste.

    @BeforeAll: Roda uma única vez antes de todos os testes da classe. CUIDADO (Lição de Prova): No JUnit 5, métodos com @BeforeAll (e @AfterAll) obrigatoriamente precisam ter a assinatura static.

    @AfterAll: Roda uma única vez após todos os testes.

    @Disabled: Pula (desabilita) o teste.

Asserções (A Verificação do Resultado):

    fail("mensagem"): Força a falha do teste imediatamente.

    assertEquals(esperado, obtido): Verifica se os valores são iguais.

    assertNotEquals(esperado, obtido): Verifica se são diferentes.

    assertTrue(condicao) / assertFalse(condicao): Verifica lógicas booleanas.

    assertNull(objeto) / assertNotNull(objeto): Verifica a existência (ou não) de instâncias em memória.

    assertSame(esp, obt) / assertNotSame(esp, obt): Verifica se apontam para o mesmo endereço de memória (não apenas se os valores são iguais).

Asserções de Exceções (Pegadinha Clássica de Prova):

    assertThrows(Exception.class, () -> { metodo(); }): Verifica se o método lança a exceção esperada.

    assertDoesNotThrow(() -> { metodo(); }): Verifica se o método NÃO lança exceção. (Atenção: Na sua prova você escreveu assertNotThrown, a sintaxe correta é assertDoesNotThrow).

Bloco 2: JUnit 5 - Testes Parametrizados (Data-Driven Testing)

Aqui é onde a prova te ataca com força. Testes parametrizados rodam o mesmo teste várias vezes com dados diferentes. Usa-se @ParameterizedTest no lugar de @Test.

Fontes de Dados (Sources):

    @ValueSource(ints = {1, 2, 3}): Passa valores estáticos simples. Limitado a um único argumento por vez (1D). Não serve se a prova pedir para testar um "input" e verificar um "output" simultaneamente.

    @CsvSource({"21, 100", "42, 200"}): Passa pares/conjuntos de valores diretamente no código, separados por vírgula.

    @CsvFileSource(files = "caminho/arquivo.csv", numLinesToSkip = 1, delimiter = ';'): Lê dados de um arquivo externo.

        Lição de Prova: Se o arquivo tem cabeçalho ou dados inúteis nas primeiras linhas, use numLinesToSkip (Ex: Para ler a partir da linha 5, pule 4 linhas: numLinesToSkip=4).

    @MethodSource("nomeDoMetodo"): Busca os dados em um método Java.

        Lição de Prova: Se o enunciado disser "fornecidos por meio de um método de provimento de argumentos", você tem que usar @MethodSource. Esse método deve retornar uma Stream<Arguments> (Ex: return Stream.of(Arguments.of(obj1, obj2));).

Bloco 3: Katalon Studio - Automação Web (Caixa Preta / E2E)

Aqui o teste simula um usuário real clicando na tela. É o topo do Modelo V (Testes de Sistema).

Interação com o DOM (API WebUI):

    WebUI.openBrowser("url"): Abre o navegador no site.

    WebUI.closeBrowser(): Fecha o navegador.

    WebUI.click(findTestObject("botao")): Clica em um elemento.

    WebUI.setText(findTestObject("input"), "valor"): Escreve num campo de texto. (Erro comum: tentar usar findText para isso).

    WebUI.verifyElementText(findTestObject("obj"), "texto"): Valida se o texto dentro do elemento bate com o esperado.

    WebUI.verifyElementAttributeValue(findTestObject("obj"), "atributo", "valor", timeout): Verifica propriedades específicas (ex: se um botão está "disabled").

Ciclo de Vida Condicional (Hooks de Finalização):
O Katalon permite fechar ou limpar o ambiente dependendo do resultado do teste. Esta é a maior pegadinha da P2:

    @SetUp: Roda antes de tudo (bom para openBrowser).

    @TearDown: Roda no final, não importa o que aconteça.

    @TearDownIfPassed: Roda APENAS se o teste foi um sucesso. (Ex: "fechar navegador apenas se bem-sucedido").

    A diferença crucial:

        @TearDownIfFailed: Roda se a asserção falhou (Ex: você esperava que o resultado fosse 10, mas o site mostrou 5. O teste rodou perfeitamente, mas a regra de negócio falhou).

        @TearDownIfError: Roda se o script quebrou (Ex: o site caiu, a internet desconectou, ou o Katalon não achou o botão HTML para clicar. É um erro de infraestrutura/código, não de regra de negócio).
